## Шар 0 — Каталог, матеріали, постачальники, ціни

**Статус: розгорнуто і живе.**

Таблиці: `product_templates`, `product_categories`, `product_category_links`, `materials`,
`material_categories`, `bom_groups`, `template_bom_items`, `template_extra_costs`,
`template_files`, `suppliers`, `supplier_contacts`, `supplier_category_links`,
`supplier_prices`, `supplier_price_history`, `exchange_rates`, `profiles`.

Функціонал: каталог шаблонів будинків з фото/файлами (галерея, PDF-превʼю), BOM
(матеріали по групах), додаткові витрати, порівняння шаблонів, довідники матеріалів/
постачальників/категорій (вкладені, з ручним сортуванням), ціни по товару і по
постачальнику (з історією змін, аудитом, фільтром по дереву категорій), Supabase Auth
з ролями (admin/manager/accountant) та RLS-політиками по ролях.

## Шар 2 — CRM / Продажі

**Статус: розгорнуто і живе — 2026-08-07.**

Таблиці (уже існували в базі до цього раунду робіт, RLS увімкнено, тимчасова політика
`authenticated_full_access` до Шару 7): `leads`, `lead_contacts`, `deals`, `deal_services`,
`deal_activities`, `deal_attachments`, `pipelines`, `pipeline_stages`, `service_rate_cards`,
`team_members`. Категорії лідів/угод використовують спільну з Шаром 0 таблицю
`product_categories`. Kanban-дошка читає готове view `v_deals_kanban` (агрегує лід +
угоду + шаблон + послуги + останню активність + дні без уваги в одному запиті).

Функціонал, перенесений з прототипу (`moduler-pro-crm-kanban.jsx`) на живі дані:
- Kanban-дошка по воронках (`Продаж будинків`, `Послуги`) з етапами, пошуком за
  іменем/регіоном, фільтром за категорією (з деревом), кнопкою "Далі →" для
  просування угоди по етапах.
- Картка ліда/угоди: контакти, шаблон або кастомний запит з площею, кількість,
  послуги (монтаж/доставка/фундамент/під ключ) з розрахунком за тарифом /
  середнім / вручну (тарифи — з `service_rate_cards`), автоматична ціна
  виробництва (шаблон: `area_m2 × base_cost_per_m2`; кастом: орієнтовно за
  середньою ціною по каталогу), відповідальний (з можливістю додати нового).
- Історія спілкування (дзвінок/telegram/email/зустріч/інше) з файлом-вкладенням
  (Supabase Storage, бакет `deal-files`) і нагадуванням "наступний контакт".
- Звіт "ліди без уваги" — сортування за кількістю днів з останньої активності,
  з підсвіткою прострочених нагадувань.
- Налаштування: перейменування/додавання/видалення/сортування воронок і етапів
  (з захистом від видалення, якщо в них є угоди). Категорії будинків — спільні з
  каталогом, керуються на вкладці "Категорії" (Шар 0), окремої вкладки в
  налаштуваннях CRM немає, щоб не дублювати той самий довідник.

### Свідомі спрощення відносно прототипу
- "Середні" оцінки вартості послуг (`AVERAGE_ESTIMATE`) — поки що фіксовані
  константи в коді, а не окремі рядки в `service_rate_cards` (`is_average`), бо
  таких рядків ще немає в базі.
- Файли по угоді прикріпляються до конкретного запису історії спілкування
  (`deal_activities.attachment_*`), окремої "бібліотеки файлів" угоди
  (`deal_attachments`) в UI поки немає — покриває основний сценарій без
  дублювання UI.

### Деплой
Той самий Next.js застосунок і той самий Vercel-проєкт, що й Шар 0 (не окремий
Vite-проєкт і не Netlify) — push у `main` автоматично деплоїть весь застосунок,
включно з новою вкладкою "CRM".

### Оновлення (2026-08-07, другий раунд)
- Категорія ліда стала множинним вибором (нова таблиця `lead_category_links`,
  бекфіл зі старого одиничного `leads.category_id`), тегами — за аналогією з
  категоріями шаблону будинку.

## Шар 3 — Виробництво

**Статус: розгорнуто і живе — 2026-08-08.**

Нові таблиці: `production_sites` (4 майданчики: Франківськ, Кам'янець, Львів 1,
Львів 2 — `responsible_person`/`capacity_units_per_month` редагуються прямо в
календарі), `production_slots` (виробничий слот: `site_id`, `deal_id` nullable
FK → `deals` з `ON DELETE SET NULL`, `start_date`/`deadline`, `status`: вільний
/ заброньований / в роботі / готово), `production_stages` (чек-лист етапів
юніта: каркас/стіни/дах/оздоблення/готово до самовивозу, `completed_at`,
каскадно видаляється зі слотом).

RLS: читання — будь-який залогінений користувач; запис — тільки admin/manager
(`current_user_role()`, той самий патерн, що в Шарі 0), без anon-доступу. Це
перший шар, де свідомо не використали "authenticated_full_access на все".

Функціонал:
- **Календар майданчиків** — Gantt-подібний вигляд (рядки = майданчики,
  колонки = тижні, 8 тижнів на екран, навігація ← Сьогодні →), слоти —
  кольорові плашки за статусом, клік відкриває картку юніта.
- **Картка юніта** (`SlotModal`) — майданчик, дати, статус, прив'язана угода
  (пошук серед угод воронки "Продаж будинків"; угода, вже прив'язана до іншого
  слота, у списку не показується), чек-лист етапів з датами завершення
  (клік по колу — позначити/зняти), видалення слота.
- **Дашборд завантаженості** (`ProductionLoadWidget`) — % зайнятості кожного
  майданчика на 4 тижні вперед відносно `capacity_units_per_month`. Винесений
  в окремий компонент, що читає власний контекст (`useProductionData`) — щоб
  вставити його на майбутній CRM-екран, достатньо імпортувати компонент і
  обгорнути це місце в `<ProductionDataProvider>`.

### Дизайн
Шар 3 (і надалі — операційні шари 4-6) свідомо отримали окрему темну
"індустріальну" візуальну тему (`.ops-theme` в `globals.css`, палітра/шрифти
з прикріпленого прототипу `moduler-pro-finance.html`: IBM Plex Mono + Space
Grotesk, амбер/ціан/іржа на темному тлі) — відмінну від світлої теми
Каталогу/CRM. Технічно це не окремий набір компонентів: `.ops-theme`
перевизначає ті самі CSS-змінні (`--bg`, `--card`, `--accent`...), які вже
читають `.card`/`.btn`/`.modal`/`table`/`.section-details` — тож усі спільні
компоненти самі перефарбовуються всередині цієї обгортки, без дублювання CSS.

## Аудит безпеки (проміжний, 2026-08-08)

- **Виправлено:** таблиці `leads`, `deals`, `transactions` мали політики RLS
  `SELECT` для ролі `anon` (без логіну) — судячи з усього, додані раніше, щоб
  автономні HTML-прототипи (як-от `moduler-pro-finance.html`, що ходить у
  Supabase напряму з anon-ключем у коді) могли працювати без авторизації. Це
  означало, що контакти лідів, суми угод і фінансові транзакції були публічно
  читабельні. Політики видалено — тепер доступ лише для залогінених
  (`authenticated`).
- **Наслідок вище:** якщо `moduler-pro-finance.html` десь реально
  використовується як окрема сторінка (не через наш Next.js застосунок), вона
  перестане отримувати дані — фінансовий дашборд потребує переведення на
  логін через наш застосунок (Шар 5, ще не перенесено в Next.js).
- **Відкрите питання:** ролі в базі (`user_role`: admin/manager/accountant) не
  відповідають таксономії ролей із Шару 7 цього документа (Власник/Продажі/
  Виробництво/Закупівля/Маркетинг). Поки що всі нові шари (2, 3) пишуть
  RLS-політики на основі вже наявних ролей (читання — всім залогіненим, запис
  — admin/manager) — свідомо не чіпали Шар 0 політики. Коли дійде черга Шару 7,
  доведеться або розширити `user_role`, або ввести окрему модель ролей і
  переписати політики на Шарах 0/2/3 одночасно.
- View `v_monthly_pnl`, `v_deal_pnl`, `v_cumulative_net_profit` (Шар 5) вже
  існують у базі, але не підключені до Next.js застосунку — тільки до
  автономного HTML-прототипу.
